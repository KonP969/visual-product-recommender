# Visual Product Recommender

**🇬🇧 English** · [🇵🇱 Polski](README.pl.md)

**What it does, in plain terms:** you upload a photo of a room and get interior doors
matched to it by colour and style. Then you narrow the result down in words, say
"something darker", "no glass", "loft style", without uploading the photo again.

![The app matching a dark modern living room to graphite and grey doors](docs/assets/screenshot.jpg)

*A dark, modern room to graphite and grey doors. The style description on the left is
generated by the model; the filters under it narrow the result.*

## Why similarity alone isn't enough

People pick doors by eye and describe them in words. The search has to handle both at
once.

Vectors catch similarity and stop there. Ask for doors with no glass, you got glazed
ones. Ask for black, you got dark brown. Rewording the prompt didn't help, because a
vector can encode neither negation nor a hard colour.

So at import time I compute three attributes for each product and store them alongside
it: colour family, whether it has glass, and style. The search filters on those hard,
inside the same query that computes similarity. The rest of the similarity can be pulled
from the vector.

## How it works

```
LIVE, on every search
  photo of a room → Gemini Flash → CLIP ViT-B/32 ┐
                     describes       text to vector │
                                                    ├→ ChromaDB → MMR + dedup → 10 results
ONCE, at catalogue import                           │   similarity   collapses repeats
  XML feed → product attributes ────────────────────┘
             colour · glass · style     (where filters)
```

Hard filters aren't a separate stage. They go into the query alongside the vector,
because that's the only way "no glass" actually means zero glass.

### What happens in the "MMR + dedup" step

Without this stage the top ten is often ten near-identical doors. That happens for two
different reasons, so there are two remedies.

**Collapsing variants (dedup).** The feed carries several entries under an identical
name: the same model in the same colour, from different price lines. In a grid they look
like repeats of one product. So I collapse them into a single card showing the
best-matching variant, the cheapest price ("from 1,051 zł") and how many variants wait in
the configurator.

**Diversification (MMR).** Even with the repeats gone, similarity search likes to return
ten variations on one idea, because they all sit close to the query. MMR (Maximal
Marginal Relevance) picks ten out of a larger candidate pool, scoring each next one not
only on how well it matches the query but on how much it differs from the ones already
chosen.

## Where the model got it wrong most often

All four of these passed the tests. They surfaced only when I sat down and looked at real
results on a real feed.

**1. Green doors classified as black.**
The classifier said: black. Reality: sage green. The "Szałwia" finish had no colour rule
of its own, so classification fell back to the English description. There, the word
*black* described a **black glass insert**, not the door leaf. Searching "black doors"
returned green ones. 68 variants with the wrong colour.

**2. Black doors classified as white.**
The classifier said: white. Reality: a black frame. A line of plain glass panels names
the variant after the glass type, for example "matte pane". The description read *white
frosted*, which referred to the **opacity of the glass**, not the frame. The frame on all
11 SKUs is black.

**3. Entrance doors passing as interior ones.**
The classifier guessed the type from the name. Reality: the type is stated outright in
the feed. Anything unrecognised defaulted to "interior", along with technical, sliding
and apartment entrance doors. 1,919 variants across 88 models; the catalogue went from
10,873 records to 6,360.

**4. The variant counter counted the wrong set.**
It counted variants in the search pool. What mattered was variants in the whole
catalogue. The card showed the number seen in that one search, so it almost never matched
the manufacturer's configurator. A true number answering the wrong question.

Which is what real human-in-the-loop work looks like: **tests check that the code does
what you wrote. They don't check whether you wrote the right thing.** All four bugs
passed 259 green tests and surfaced only when someone looked at actual doors.

## And what couldn't be done?

Style recognition that matches reality.

Take Scandinavian. One door model comes in a dozen or so colours, and style is assigned
to the whole model, not to an individual colour. For most styles that works: a loft door
is a loft door whether it's black or oak.

Scandinavian doesn't behave that way, because colour is exactly the point. Pale wood. The
same model in dark oak isn't Scandinavian any more. And since nearly every model ships in
both pale and dark finishes, none of them collects enough votes from the model to earn
the label.

## Running it

Needs Node.js, Python and a Google AI Studio API key. Four processes:

```bash
# 1. vector store
chroma run --path ./chroma_db --port 8000

# 2. CLIP model (first start loads the model, ~30 s)
cd python-sidecar && venv\Scripts\activate && uvicorn main:app --port 8001

# 3. backend
cd backend && npm run dev          # http://localhost:3001

# 4. frontend
cd frontend && npm run dev         # http://localhost:5173
```

Copy `backend/.env.example` to `backend/.env` and put your own Gemini key in it. Import
the catalogue from the admin panel in the UI (XML product feed).

Operational notes: `CLAUDE.md`.

## A note on the data

The catalogue comes from the public XML product feed of the company I work for. The feed
is published openly for retail partners and price comparison sites. The app does not copy
product images, it loads them straight from the manufacturer's CDN, the same way any
partner using that feed does. The only image in this repository is the screenshot in
`docs/assets`, showing the working interface.

I built this after hours, on my own account. It isn't an official product of the
manufacturer.
